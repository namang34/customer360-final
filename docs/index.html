Agentic Customer 360

It reads a bank customer’s activity as it happens, works out what is going on in their life, and decides whether the bank should reach out.

Built for the Inter IIT Tech Meet 15.0 Prepathon.

This customer is slowly leaving the bank. The system holds back on 15 February, when the evidence is thin. It does not treat the tax refund as a reason to sell them something. It escalates three days before the 8 March checkpoint, which is after the cancel-instructions page was opened on 4 March and before the first large transfer on 6 March.

How it works

Four agents each watch a different part of the bank and report what they see. A synthesis step combines those reports into a single reading of the customer’s situation. Only then does the system consider acting, and every action has to get past three checks and a person.

Before the bank acts

  1. Confidence. Below high confidence, the only action allowed is none.
  2. Guardrail. A fraud hold, a relationship manager escalation or a personalised offer needs at least two independent source systems and two distinct events. This check is arithmetic and set membership. No model is consulted.
  3. Critique. Code checks that the evidence is corroborated, backed by a policy and not contradictory. A model reviews only whether the response is proportionate. A sales offer to a customer in distress is refused on what it means, however strong the evidence.
  4. Human review. Any action other than none goes to a person for approval.

No agent sees the future

No agent can see an event later than the simulated present. The replay engine releases each event no earlier than it happened, and the memory layer filters on the same rule with the cut-off date as a required argument. A test checks that the two agree at all 74 daily checkpoints in all three scenarios. Late-arriving events stay invisible until they arrive, so lead times are not flattered by hindsight.

Rules that are enforced in code

Explainability
The output writer refuses to build any action row whose notes do not cite at least one event ID.
Traceability
One trace record per checkpoint, with the findings, guardrail verdict, critique verdict and routing.
Privacy
Names and identifiers are replaced with stable tokens before any prompt or log line. A test searches the real output for the customer’s name.

The language models did worse

All three scenarios were also run live, with 231 model calls and no fallbacks. On 20 February in scenario 2 the live models read a new-child pattern as income disruption and kept that reading for seventeen days before correcting it. That loses a graded checkpoint: offline scores 8/8, live would score 7/8. So the headline numbers are the offline ones.

What building it taught

These are the lessons recorded in the project’s own evaluation write-up, including the ones that reflect badly on the first version.

A fallback can hide a bug

Every model call has a deterministic fallback, so a failure never kills a run. The same property made a broken live setup look healthy: it printed “live LLM”, finished, and scored 8/8, because those were the offline scores. Five defects sat behind the fallbacks until the live path was measured, including a .env file that was never loaded. compare_live.py now warns when a “live” run made no successful model calls.

Measure the model instead of assuming it

On 20 February in scenario 2, the live models read a new-child pattern as income disruption for seventeen days and lost a graded checkpoint. Keyword matching and arithmetic got it right. The models stay in for reading free text. Corroboration and the guardrail stay arithmetic.

Test the rule you chose not to use

The check that asks whether two agents have flagged something is recorded on every day but not enforced. Wiring it in as a real gate dropped the score from 8/8 to 6/8, because that same step is what carries a belief forward on quiet days.

An alert that fires every day stops being read

The first version of the review queue raised 38 items for scenario 1 by restating the same two sources every day for five weeks. It now raises an item only when the picture changes, and a test caps it at ten.

Say what the score does not prove

The thresholds were calibrated on the same eight checkpoints they are scored on, so 8/8 confirms the calibration and says nothing about generalising. The write-up says so, and publishes the live 7/8 next to the offline 8/8.

Hindsight flatters lead times

A system that sorts events by when they happened would claim to have known about two planted late events days before it could have. The replay releases each event only once it has arrived, so the 5, 8 and 3-day lead times are not inflated.

The full account is in docs/EVALUATION.md.

What this does not prove

The project’s own evaluation write-up lists these. They are worth reading before trusting any number above.

  • The confidence thresholds were calibrated against the same eight checkpoints they are scored on. 8/8 confirms the calibration was applied correctly. It is not evidence that the system generalises.
  • Eight graded checkpoints, four false-positive checks and three lead-time targets are the whole sample. Every percentage here has a single-digit denominator.
  • Five of the fourteen possible states can never be produced: fraud or takeover, elder scam risk, small-business cash flow, job change or promotion, and retirement. A held-out scenario of those kinds would score zero on state and action.
  • The detector for stopped standing instructions never fires on this data. The practice scenarios are missing their February instructions, and a one-missed-cycle rule could not tell that apart from a real cancellation.
  • The live model path is the least tested part. Every test runs offline, and the file that makes live calls has 38% line coverage.
  • When its embedding model cannot be downloaded, document retrieval falls back to a simple word-count embedder. It works on this small corpus but has no semantic generalisation.

Full detail: docs/EVALUATION.md.

Run it yourself

The offline path needs no API keys, which is what makes the results reproducible.

git clone https://github.com/namang34/customer360-final
cd customer360-final
pip install -r requirements.txt

python -m pytest tests/ -q                    # 238 tests
python run_evaluation.py                      # run and score all three scenarios
python watch.py data/scenario_03 --speed 2    # watch it think, about 2.5 minutes

Add --live to run_evaluation.py or watch.py to use the Gemini and Groq models set in .env. compare_live.py runs the offline and live paths side by side.
