# Held-out scenario h1: account takeover

A fourth scenario, written **after** the three graded ones, to ask whether the
system generalises. It does not. This folder records that, so the result is not
lost.

## Read this first

- It is **synthetic**, generated by `generate.py` (customer "Jordan Ellis", CUST_00901).
- It was **written by an AI assistant (Claude) after reading this repository's code**,
  not by the challenge organisers. That cuts both ways: I knew the 10,000
  large-transfer threshold in `agents/transaction.py` when choosing amounts, and
  I wrote the ground truth myself. It is a stress test, not an independent benchmark.
- It is **not part of the graded evaluation**. `run_evaluation.py` globs
  `data/scenario_*`, so this folder is never picked up by default. The graded
  result (8/8 offline) and the 238 tests are unchanged.

## What happens in it

On 21 to 22 Feb an attacker logs in from a new desktop, changes the contact
details, adds a payee, raises the limit, drains savings (15,000 and 11,000),
sends five instant transfers (each under 10,000), and buys gift cards. The
customer opens an "unauthorised_transactions" ticket on 22 Feb. Expected from a
good system: `potential_fraud_or_takeover`, high confidence, `compliance_fraud_hold`,
escalated, by the 22 Feb checkpoint.

## Run it

```
C360_OFFLINE=1 python run_evaluation.py --scenario data/held_out/h1_account_takeover --out out_h1
```

## Result (offline, deterministic)

| Checkpoint | State | Confidence | Action | HITL |
|---|---|---|---|---|
| 20 Feb (quiet) | pass | pass | pass | n/a |
| 22 Feb | fail: `financial_distress_general` / `no_significant_event` | fail: low | fail: `no_action` | fail |
| 24 Feb | fail | fail | fail | fail |

Lead time: fail, `compliance_fraud_hold` never fires. Overall about 33%.

## Why it fails

1. **Perception is blind to most of the attack.** Only two savings-drawdown findings
   were produced. The five transfers sit under the 10,000 absolute threshold
   (a threshold I had read before choosing them).
2. **The customer's own ticket is ignored.** `support.py` emits `complaint_open`
   only for `GRIEVANCE_CATEGORIES`, and `unauthorised_transactions` is not one.
   Re-filing it under a category the system does know (`dispute`) was tested: the
   state moves to `financial_distress_general`, still not fraud, still `no_action`.
3. **A blocked transfer is counted as a sweep.** The 3 Mar blocked attempt reads
   as money leaving.
4. **Synthesis has no fraud state.** `STATE_AFFINITY` has no entry for fraud or
   takeover, so no combination of findings can select it.

## What it does and does not show

- The failure mode is **silence, not a wrong action**: the system never takes a
  harmful step, it just misses the fraud.
- The three false-positive checks report "clean" here, but that is **vacuous**,
  because the system never acts at all.
- One scenario written by one author after reading the code is thin evidence.
  It shows a real gap, not its size.
